# UX-M2 — Product Polish Review

**Milestone:** UX-M2 (usability, clarity, polish and presentation only)
**Date:** 2026-09-28
**Scope rule:** no new capability. No SharePoint or Question Bank integration, no new reporting
feature, no new AI feature, no badges engine, refreshers or certificates. Every change below is
copy, layout, disclosure or presentation over data the screens already had.
**Authority:** `docs/ui/KNOWZY_UI_SOURCE_OF_TRUTH.md` and the capability matrices still decide what
a screen may show. This document records a review against them; it does not amend them.

## 2. UX findings

Each finding is what a first-time or non-technical user met on the screen as it stood.

| # | Screen | Finding | Severity |
| --- | --- | --- | --- |
| F1 | Generate | The intro described the governance rule ("an explicit document selection and a recorded preflight decision") instead of the task. A new author could not tell what the page was for. | High |
| F2 | Generate | "Run preflight" is internal vocabulary. Nothing on the button said it checks the documents. | Medium |
| F3 | Generate | The source was named twice — in the hero and in the selector under it. | Low |
| F4 | Generate | Before pressing Generate the screen did not answer, in one place: which documents, which model, how many, whether anything blocks it, and what happens next. The answers were spread over six fields and a result panel. | High |
| F5 | Review Queue | A row showed the question text and a "Drafted by <model id>" note. The evidence — the thing a reviewer judges — was only on the question page, so every row had to be opened. | High |
| F6 | Review Queue | A 12-character section hash printed under each document name. It means nothing to a reviewer. | Low |
| F7 | Review Queue | Up to 100 tall rows on first load made a very long page. | Medium |
| F8 | Review Queue | Confidence and similarity at three decimals implied a precision nobody acts on. | Low |
| F9 | AI Providers | The page answered an engineer's questions (gate state, readiness ladder, capability flags) and never a business user's: *can I use it, and what happens if I pick it?* | High |
| F10 | AI Providers | A provider that is both unapproved and not built read only "BLOCKED_BY_APPROVAL" (the checks run most-permanent first), so approval looked sufficient when it is not. | Medium |
| F11 | AI Providers | Five capability badges per row made every row tall; they are reference, not action. | Low |
| F12 | Reports | Every KPI card printed its SQL-like formula as a caption. In a demonstration it read as fine print on eight cards. | Medium |
| F13 | All | A refusal panel gave the reason and code but rarely the next step, and several generation controls (not approved, over budget, justification required) rendered as generic errors rather than refusals — "something broke" when a control was holding. | High |
| F14 | AI Usage & Budgets | The intro listed four accounting terms; the budgets note did not say what happens when a limit is reached. | Low |

## 3. Polish changes, with before/after rationale

### 3.1 Generate (F1–F4)

| Before | After | Why |
| --- | --- | --- |
| Intro: "Generation requires an explicit document selection and a recorded preflight decision…" | "Choose the documents, check what they can support, then generate draft questions. Every draft is reviewed and approved by people before anything is published." | Task first; the governance promise in words a user repeats. |
| Step 1 "select documents", Step 2 "read the checks and choose an action" | "choose documents", "check what the documents support" | Same steps, plainer verbs. |
| Button **Run preflight** | **Check documents** | Says what it does. The preflight record, API and audit are unchanged. |
| Source named in the hero *and* above Step 1 | Stated once: "Documents come from: <source>", or the selector when there is a choice | One place to read it. |
| No summary | **Before you generate** at the top of Step 3: Documents (count + first three names), Generated by (provider + model), Questions ("Up to n. Fewer if the documents do not support more — never padded."), Status (Ready, or needs a justification), What happens next | Answers the five questions the brief names. Every value is what the form will send; it follows the fields as they change and is re-read after React's post-action form reset. |

The requested count is still a ceiling (EVAL-M1), and the summary says so rather than promising n.

### 3.2 Review Queue (F5–F8)

| Before | After | Why |
| --- | --- | --- |
| "Drafted by gpt-5.3-codex_codeassist" as small text | A badge: **AI · <model>** (AI tone), **Template generator**, or **Imported from a file** | Scannable; a mixed queue can be read apart at a glance. |
| Domain · topic on its own line | Beside the badge on one line | Filing and origin together. |
| No evidence in the list | The first ~160 characters of the evidence span, quoted, cut at a word | A reviewer can judge the row before opening it. |
| Section hash under the document name | In the element's `title` (tooltip) | Kept for lineage tracing, out of the reading path. |
| Up to 100 rows | 25, then **Show 25 more**, up to the API's 100 | Shorter first page; the tab counts remain true totals. |
| `0.734` | `0.73` | Precision a person acts on. |

### 3.3 AI Providers (F9–F11)

- **At a glance**, a card per provider before the technical table: a plain status (**Ready to use**,
  **Waiting for approval**, **Not set up yet**, **Paused — budget spent**, **Not suitable for this
  use**, **Not included in this release**), **If chosen on Generate** (what would actually happen),
  and **Why** (the platform's own reason, unchanged). The deterministic provider is named **Template
  generator (built in)** and described as "No AI, no network and no cost".
- Derived from the gate state alone — nothing new is computed, and `OVER_BUDGET` still comes only
  from the usage read model.
- An unapproved provider that is also unregistered adds: *Also not included in this release: an
  approval alone will not make it usable.*
- Cards, not a second table: the technical table's rows are located by provider id, and a second grid
  of rows would have been a second place to read one state from.
- The five capability badges per row are behind **Declared capabilities** (native `<details>`).

### 3.4 Reports (F12)

The eight KPI captions moved into one **How these figures are calculated** disclosure under the
cards: every card's label and formula as a definition list, followed by the comparison rule that was
previously a free-standing paragraph. Nothing is removed; the formulas are one keyboard-reachable
click away. Full reports keep their always-visible "How every number here is calculated" section.
The comparison copy is untouched and still rendered only by `KpiComparison`.

### 3.5 Empty, loading, error and disabled states (F13)

- `components/Problem.tsx` adds **What you can do** for seventeen common codes (permission,
  separation of duties, gates, justification, preflight, selection, empty scope, the four provider
  refusals, budget, concurrency, timeouts, version conflicts). The server's detail stays the reason;
  the code and HTTP status stay visible.
- Ten codes — eight generation controls and two taxonomy refusals — now render as **refusals** (the
  platform declined) rather than errors, per the component's own three-state rule: a control holding
  is not a fault.
- Loading and empty states were not changed in this milestone; they use the shared `EmptyState` and
  loading components. A wording pass over them is debt D8.

### 3.6 AI Usage & Budgets (F14)

Intro rewritten around what the page answers (how much was used, what it cost where measurable, how
close each provider is to its limits), and the budgets note now explains a token and says generation
is refused until the period rolls over when a limit is reached. No figure changed.

## 4. Consistency review

| Element | Finding | Action |
| --- | --- | --- |
| Buttons | Generate's primary actions (Check documents, Record decision, Generate questions) are primary-tone; filters and paging are secondary-tone. | None needed. |
| Disclosures | Native `<details>` with an underlined info-tone summary is now used for validation chains, capabilities and formulas. | Adopted as the pattern. |
| Badges | Status badges use the shared tone map; generator badges use `AiBadge` only for model-drafted rows. | Consistent. |
| Tables | DataTable with hidden captions throughout; the new provider overview deliberately is not a table (§3.3). | — |
| Forms | GET filter forms (source, generator) share Field + Select + secondary Button. The Show button sits a few pixels lower than the select's baseline. | Debt D5. |
| Preview pages | Learner previews keep `ExampleRegion` framing; untouched. | — |

## 5. Screens reviewed and not changed

- **Dashboard, Sources, Publish/Assessments:** primary actions are already the dominant buttons and
  the copy was reworked in UI-M3/UX-M1. Changes here would be taste, not a finding.
- **Learner Portal:** the quiz, integrity and scoring screens are governed by non-negotiables
  (answer-key protection, deterministic scoring); previews are governed by LIVE-PREVIEW rules. No
  finding justified touching them in a polish milestone.

## 6. Responsiveness review

Measured in Chrome after the changes, `document.documentElement.scrollWidth` against the viewport:

| Route | 390px | 820px |
| --- | --- | --- |
| `/generate` | 390 / 390 | 820 / 820 |
| `/review` | 390 / 390 | 820 / 820 |
| `/review?queue=published` | 390 / 390 | 820 / 820 |
| `/administration/providers` | 390 / 390 | 820 / 820 |
| `/reports` | 390 / 390 | 820 / 820 |
| `/` | 390 / 390 | 820 / 820 |

No horizontal scroll. The provider cards collapse from three columns (xl) to two (md) to one; the
Generate summary's two-column definition list collapses to one below `sm`. The responsive-nav specs
(drawer, rail, sidebar, no sideways scroll at 390/820/1440) pass.

Full-page heights at 1440px after the change, for reference (not compared with a before figure,
which was not measured): Generate 1,218px (before a preflight), Review author queue 5,691px at 25
rows, AI Providers 3,498px, Reports 4,224px, AI Usage 4,775px.

## 7. Remaining UX debt

| # | Debt | Why not in UX-M2 |
| --- | --- | --- |
| D1 | The technical provider table is still seven columns and tall per row. A detail drawer per provider would suit it better. | A structural rework of an administration screen; the overview now serves the non-technical reader. |
| D2 | "Why" on provider cards quotes the platform reason, which can name `llm.approvedProviders`. | The reason string is the server's and is also audited; rewording it belongs with the API. |
| D3 | Review rows grew taller with the evidence excerpt; 25 rows is ~5,700px. A compact/expanded toggle would help heavy reviewers. | Needs a per-viewer preference. |
| D4 | The preflight results (Step 2) are still dense: six checks per document with facts. A per-document summary line with the checks behind a disclosure would reduce it. | Preflight copy is asserted by several specs; worth its own change. |
| D5 | Filter form buttons sit slightly below the select baseline. | Shared Field layout; fix in shared-ui with a visual check across screens. |
| D6 | Provider display names for unbuilt providers are their ids (ANTHROPIC, GEMINI). | Display names are declared data in the registry, not copy. |
| D7 | Refusal "What you can do" covers seventeen codes; the rest show reason and code only. | Added where a user is likely to meet them. |
| D8 | Empty and loading states were not given a wording pass. | Not reached in this milestone. |
